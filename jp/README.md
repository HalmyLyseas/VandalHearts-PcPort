# Vandal Hearts (Japan) — SLPM-86007 matching decompilation

A byte-exact matching decompilation of the Japanese PlayStation release of *Vandal Hearts*
(Konami, SLPM-86007). Every translation unit is C; rebuilding the tree reproduces the original
executable bit-for-bit.

```
53849277b08184863bd45f10925995a6  SLPM_860.07
53849277b08184863bd45f10925995a6  build/SLPM_860.07
```

## Status

**Complete — 88 / 88 translation units, verified from a clean tree.**

The only assembly left in the two program blocks is the statically-linked Sony PsyQ SDK
(`[0x800c96f8, 0x800e69f8)`, 149 library functions); all game code is decompiled C. `make check`
is the sole correctness signal — nothing is "done" until the md5 matches.

This is an independent project. The North American release's decompilation
([HalmyLyseas/VandalHearts-PcPort]) was used as a *reference corpus* while working, never as an
assumed answer: every function here is re-proven against the Japanese binary. That corpus is not
required to build, and is not part of this repository.

## What you must supply

Nothing copyrighted or proprietary is distributed here. Three inputs come from your own copy and
your own toolchain fetch:

| input | where it goes | notes |
|---|---|---|
| `SLPM_860.07` | repo root | the base executable from your own legally-owned disc — md5 `53849277b08184863bd45f10925995a6` |
| Sony PsyQ SDK headers | `include/PsyQ/` | the SDK's `INCLUDE/` directory (PsyQ v3.3). DOS-era CRLF text — see the grep note below |
| toolchain | `external/` | old-gcc `cc1` (v2.6.3 + v2.5.7) and `maspsx`; upstream URLs in `external/references` |

## Prerequisites

- `python3`
- [`splat`](https://github.com/ethteck/splat) — tested with **0.50.0** (`python3 -m splat split`)
- `mipsel-linux-gnu-{as,ld,objcopy,objdump,nm}` — binutils, tested **2.46.1**
- The `external/` toolchain: [`old-gcc`](https://github.com/decompals/old-gcc) built `cc1`
  binaries and [`maspsx`](https://github.com/mkst/maspsx). `external/toolchain/bin/` holds the
  `cc1_v263_decompals` / `cc1_v257_decompals` names the Makefile expects; prepend it to `PATH`.

The cross triple is not load-bearing — the artifact is a raw `objcopy -O binary`, so only
instruction encoding matters. A modern `mipsel-linux-gnu-gcc` is **not** used; the build compiles
with the prebuilt old GCC 2.x `cc1` only.

## Reproducing the build

```sh
# 1. inputs
cp /path/to/SLPM_860.07 .
cp -r /path/to/PSYQ/INCLUDE/* include/PsyQ/

# 2. generate the splat config, extract, and fix up the linker script
python3 tools/gen_yaml.py                             # SLPM_860.07.yaml from tools/tus.txt
python3 -m splat split SLPM_860.07.yaml < /dev/null
python3 tools/fix_linker_align.py                     # MUST run after every split
python3 tools/gen_assets_inc.py                       # disc-derived C initializer includes
python3 tools/finalize_build.py < /dev/null

# 3. build and verify
find asm assets src -type d | sed 's|^|build/|' | xargs mkdir -p
PATH="$(pwd)/external/toolchain/bin:$PATH" \
  make PYTHON=python3 CROSS=mipsel-linux-gnu- check < /dev/null
```

`make extract` runs steps 2's splat + `gen_assets_inc` together. The final `md5sum` must print the
same hash twice.

### Gotchas that will cost you a build

- **Always redirect stdin: `< /dev/null`.** `maspsx` prefers stdin over its file argument; a build
  started with an open stdin hangs forever. This is the number-one cause of a "stuck" build.
- **Never `make … | grep`** — a pipe masks make's exit status.
- **`fix_linker_align.py` must run after *every* `splat split`**, and the linker script is **not** a
  make dependency: after a re-split you must force a relink (simplest: `rm -rf build`), or make will
  silently reuse the stale ELF.
- **Only one build at a time** over `build/` — concurrent makes truncate each other's objects.
- The PsyQ headers are DOS-era CRLF text, so plain `grep` reports zero matches against them
  (binary-file heuristic). Use `grep -a`.

## Repository layout

```
src/            the decompilation — 88 C translation units, the deliverable
include/        game headers. include/PsyQ/ is user-supplied and git-ignored; include/assets is a
                generated symlink to ../assets so `#include "assets/X.inc"` resolves via -Iinclude
tools/          the build pipeline and the verification tools (see below)
tools/tus.txt   the TU manifest: per-TU rodata/text/data/sdata ranges — source of truth
symbol_addrs.txt, undefined_additional.txt   the symbol map splat and the linker consume
SLPM_860.07.yaml   splat config — GENERATED by tools/gen_yaml.py, do not hand-edit
Makefile        cc1 -> maspsx -> as -> ld -> objcopy -> md5
asm/ assets/ build/ include/assets   generated by the pipeline; never committed
```

Everything in this repository is derived from the Japanese binary alone. Nothing is carried over
from the North American decompilation: no US sources, symbol maps, binaries or comparison tooling.
That project ([HalmyLyseas/VandalHearts-PcPort]) was used as a reference while the work was being
done: it informed naming and structure, and every translation unit was then re-proven against
`SLPM_860.07` by md5. It is not a dependency and is not reproduced here. To compare the two
releases, clone it separately and diff against this one.

### Tooling

Every tool here runs from a clone with only `SLPM_860.07` and the toolchain:

- **Build pipeline** — `gen_yaml.py` (splat config from the TU manifest), `fix_linker_align.py`
  (drop splat's spurious `ALIGN`), `gen_assets_inc.py` (regenerate the disc-derived C initializer
  includes and the `include/assets` symlink), `finalize_build.py` (dedup symbols, drain danglers).
  `maspsx` is a symlink to the vendored copy under `external/`.
- **Verification** — `verify_fn.py` compiles a TU and immediate-preserving-diffs a single function
  against the Japanese binary; `reduce_diff.py` filters that down to the real hunks. This is the
  pair to reach for when changing `src/`: `make check` tells you the image broke, these tell you
  which function and which instruction. `audit_tus.py` checks the TU manifest for range overlaps.

## Toolchain notes

The Japanese build uses the **same compiler as the US release**: `cc1` v2.6.3 at `-O1 -G8`, with
per-file overrides carried in the Makefile — `-G0` for `core/glyphs`, `world/dojo`, `world/map`,
`ui/supplies`, `world/town`, and `cc1` v2.5.7 with `-O2 -G0` for `core/audio`. v2.6.0 and v2.6.3
are byte-identical for this codebase; only v2.5.7 is a genuine outlier. A mismatch under v2.6.3 is
a C/data/relocation problem, not a compiler-version problem.
